# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install              # install deps (npm is canonical — package-lock.json is committed; bun.lock is gitignored)
npm run build             # tsup src/index.ts -> dist/ (ESM + .d.ts)
npm run dev -- <args>      # run the CLI from source via tsx, e.g. `npm run dev -- bootstrap F0001 --new-feature`
npm link                  # after building, installs the `lv` binary globally from dist/index.js
npm run mastra             # Mastra dev server at localhost:4111 — inspect agent traces/tool calls
npx tsc --noEmit           # type-check
```

There is no lint script and no automated test suite. Verify changes with `tsc --noEmit`, `npm run build`, and by actually running the relevant `lv <subcommand>` against a scratch repo/doc (see any `src/cli/*.ts` for the command it implements). **Gotcha**: `confirm()`/`promptSelect()` (`src/cli/helpers.ts`, used by `lv resume`) use `readline/promises`. Piped/non-TTY stdin (e.g. `printf "1\nn\n" | npx tsx ...`, used to script these prompts for testing) works fine _across_ separate calls with real async work in between (e.g. a git call, a file read) — but _rapid back-to-back_ `.question()` calls with no intervening await, like `promptSelect()`'s retry-on-invalid-input loop, hang on the second call. This is a Node quirk with piped input specifically; real interactive terminal use is unaffected either way.

## Architecture

`lv` is a spec-driven-development CLI with two independent pipelines that both write into `docs/` of the _target_ repo (this repo dogfoods itself — see below). LV's own job stops at handing context to [OpenSpec](https://github.com/Fission-AI/OpenSpec), which then drives explore → propose → spec → design → tasks → apply through the engineer's coding agent — there is no `lv`-side analysis/design agent or approval gate.

**1. Ticket/change pipeline** — `lv start <ticket-id>` (from a Lark ticket) or `lv start --description "<text>"` (no ticket) creates `docs/changes/<change-id>/state.yaml` (schema: `StateSchema` in `src/types.ts`) — `ticket_id` (optional — absent for description-based changes), `title`, `description`, `feature_ids`, `branch`, `created_at`, `lv_version`. This file is LV's _only_ artifact for a change and the single source of truth for its context — not LibSQL, which only holds Mastra's own thread/memory internals (used solely by `lv start`'s feature-match/split agents now). `<change-id>` is the ticket ID for ticket-based starts, or `slugify()`d from a short title derived from the description's first line otherwise; it names both `docs/changes/<change-id>/` and, once the engineer runs an OpenSpec workflow, `openspec/changes/<change-id>/` (see "OpenSpec integration" below) — same name, no separate mapping stored. There is no `lv answer`/`lv approve`/`lv design` and no `StateMachine` — once `state.yaml` exists, the engineer drives everything else through OpenSpec directly.

Branch naming is configurable, not hardcoded — `src/engine/branch-naming.ts` renders/parses branch names from `.lv.yaml`'s `branch_types` (a `{ typeName: pattern }` map, where each entry is either a plain naming-pattern string or `{ pattern: string; base_branch?: string }`; e.g. `{ feature: "feature/{ticket_id}-{summary}", hotfix: { pattern: "hotfix/{ticket_id}-{summary}", base_branch: "master" } }`; defaults to exactly `{ feature, hotfix }` as plain-string patterns if unset — `DEFAULT_BRANCH_TYPES`) plus `default_branch_type`. `{ticket_id}` and `{summary}` are the only two placeholders; `{summary}` is a `slugify()`d ticket title (or derived short title, for description-based starts), filled in by `lv start` from the fetched Lark record (or the given description). `getBranchTypes(config)` unwraps every entry to its pattern string (`Record<string, string>`), so `renderBranchName(config, ticketId, { type?, summary? })`, `matchBranch()`, and `branchGlobs()` all keep operating on patterns exactly as before, unaware of `base_branch` — `renderBranchName()` builds a name (used by `lv start`, passing a change-id where a ticket ID would go for description-based starts — the placeholder is generic text substitution, not Lark-specific) — omitting `summary` (as `lv resume`'s no-branch-found fallback does, since it has no ticket title to slugify) drops the placeholder and its preceding separator instead of leaving one dangling. `matchBranch(config, branchName)` tries every configured type's pattern against an arbitrary branch and returns `{type, ticketId}` or `null` (used by every command that re-derives the change ID from the current branch instead of taking it as an argument — `src/cli/resume.ts`, `status.ts`); it captures `{ticket_id}` non-greedily and treats "separator + `{summary}`" as an optional unit, so both a full name and a summary-less fallback name parse back to the same ID — this relies on ticket IDs (Lark Bitable record IDs, plain alphanumeric) and description-derived slugs never containing the literal separator between the two placeholders. `branchGlobs(config)` turns each pattern into a `for-each-ref` glob (both placeholders → `*`) for `listBranchesMatching()` in `src/integrations/git/client.ts`. Adding a new branch-parsing call site means calling `matchBranch()`, never re-deriving a hardcoded prefix. `resolveBaseBranch(config, type)` returns that type's configured `base_branch` (only possible via the object form) or falls back to `config.default_branch` — `lv start` resolves this once per invocation, from the branch type actually being started (`--type`, else `default_branch_type`), and passes it to both `createBranch()` (fresh start) and `discardLocalBranch()` (restart), so a gitflow-style repo can fork `hotfix` from `master` and `feature` from `develop` instead of every type forking from the same `default_branch`.

`lv resume [ticket-id]` (`src/cli/resume.ts`) only resolves and checks out a branch, then prints — it does not dispatch into any further command. Given a ticket ID it searches for branches matching it across _every_ configured type by ticket ID alone via `matchBranch()` (ignoring `{summary}`) — one match checks out directly, multiple prompts via `promptSelect()`, none falls back to `default_branch_type`'s rendered name without a summary (which will only actually exist if the change was never started, so this fallback typically just fails the subsequent checkout); given no ID it uses the current branch if `matchBranch()` recognizes it, otherwise lists all change branches and prompts. Once resolved, it reads `state.yaml` and prints the same summary as `lv status` (shared via `printStateSummary()` in `src/cli/status.ts`), then reminds the engineer to continue via their coding agent's OpenSpec workflow.

**2. Feature docs pipeline** — `lv init [--tool <tool>]` → the `lv-bootstrap` skill/command (installed by `lv init`) or `lv bootstrap <feature-id>`. `lv bootstrap` populates `docs/features/<feature-id>/{overview.md,design.md}`, independent of any ticket. Generating from real code is no longer something `lv` does itself via an LLM call — it's an `lv-bootstrap` skill (and, for a known coding-agent shape, a matching slash command) that the engineer runs from inside their coding agent: the agent runs `lv bootstrap <feature-id> --context [--paths ...]` (no LLM call — prints repo root, output paths, scan config, any existing draft, and the resolved `--paths` file list, if given), explores the repo itself (or reads only the given `--paths`) with its own tools, _refines_ any existing draft (re-verifying code facts against its own fresh exploration) rather than overwriting from scratch, writes `overview.md`/`design.md` directly, and finishes with `lv bootstrap <feature-id> --finalize --title "..."` (no LLM call — updates the feature index and syncs Lark). `lv bootstrap <feature-id>` with none of `--new-feature`/`--context`/`--finalize` now errors, pointing at the skill/command. `lv bootstrap <feature-id> --new-feature` (placeholder-only docs, no LLM call at all) is unaffected. `lv start` bootstraps a referenced feature with no `docs/features/<id>/` directory inline via that same placeholder mode (`generateFeatureDocsPlaceholder()`), not the skill flow, so it never blocks on a coding-agent turn — see `lv-start/inline-feature-bootstrap` under `openspec/specs/`.

`lv init` installs and configures OpenSpec for a chosen coding agent (`src/cli/init.ts`, no Mastra agent involved) and wires OpenSpec's context to LV. It shells out to `openspec init --tools <tool>` via `execa` (same pattern as `src/integrations/git/client.ts`'s git wrapper) — `lv` does not hardcode which coding agents are supported, whatever `openspec init --help` lists is what `--tool` accepts. It then idempotently appends a pointer into `openspec/config.yaml`'s `context:` field (`CONTEXT_POINTER_LINES` in `src/prompts.ts`) naming `docs/features/<feature-id>/{overview.md,design.md}`, `docs/changes/<change-id>/state.yaml`, and (advisory only — see Gotcha below) a convention to refresh feature docs when running `/opsx:sync` directly, so every OpenSpec workflow (`/opsx:propose`, `/opsx:apply`, ...) loads LV's context automatically. It also idempotently writes an `operations.archive.guidance` entry (`ARCHIVE_GUIDANCE` in `src/prompts.ts`) telling the generated `/opsx:archive` workflow to run `lv bootstrap <feature-id>` for each feature ID in the archiving change's `state.yaml` before completing — read via `openspec instructions archive --change <name> --json`'s `operationGuidance` field, which OpenSpec's own generated archive workflow already reads and follows. **Gotcha**: both appends are raw text operations, not a YAML round-trip, specifically to avoid stripping `openspec/config.yaml`'s template comments — each only falls back to parsing+re-dumping via `js-yaml` (losing those comments) when its target key (`context:` or `operations:`) is already active (uncommented), and `addContextPointer()` checks each of `CONTEXT_POINTER_LINES` for presence independently so a repo already wired with an older, shorter pointer only gains the lines it's missing rather than duplicating what's already there. **Gotcha**: the `/opsx:sync` convention line is unenforced — `openspec instructions` has no `sync` operation (no `operations.sync.guidance` hook exists), and the generated `openspec-sync-specs` skill never reads `context:` at all, so this is documentation an engineer/agent may or may not see, not a wired trigger like the archive guidance is.

`lv init` also installs the `lv-bootstrap` skill itself — unlike OpenSpec's own tool support (delegated entirely to `openspec init`), this is `lv`'s own content, but detection of which coding agents to install it for is still dynamic rather than hardcoded: `installLvBootstrapSkill()` checks every immediate subdirectory of the repo root for `skills/openspec-propose/SKILL.md` (the one relative shape OpenSpec writes for every tool it supports, verified across seven very different tools — see `design.md` of `openspec/changes/make-lv-bootstrap-a-skill-like-openspec/`) and writes `<tool-base-dir>/skills/lv-bootstrap/SKILL.md` for each match found — no tool names hardcoded. A slash command is additionally written only for the small, explicit set of coding-agent command-file formats `lv` has a template for (`LV_BOOTSTRAP_KNOWN_COMMAND_SHAPES` in `src/cli/init.ts` — Claude Code, Cursor, as of this change); every other detected agent (Codex included) gets the skill only, since command-file formats vary too much across tools to generalize (nested vs. flat Markdown, a separate `workflows/` dir, TOML for some tools).

**OpenSpec integration**: this repo's own `openspec/` directory (schema `spec-driven`, see `openspec/config.yaml`) is both how LV plans its own changes (this file's git history) and the template `lv init` installs into target repos. `openspec/changes/<change-id>/` (proposal.md, `specs/<capability-path>/spec.md` deltas, design.md, tasks.md) is entirely OpenSpec-owned — LV never reads or writes under `openspec/`, except the `context:` and `operations.archive.guidance` writes in `lv init`. `.claude/skills/openspec-*`, `.claude/commands/opsx/*`, and `.agents/skills/openspec-*` are what `openspec init --tools <tool>` generates per coding agent; `lv init` never edits these directly (see the `context:`-field decision above, in `design.md` of `openspec/changes/integrate-openspec-workflow/`) since they're regenerated by `openspec update`/`openspec init --force`. `lv init` does write its own `<tool-base-dir>/skills/lv-bootstrap/SKILL.md` (and, for a known shape, a command file) alongside these OpenSpec-generated files — a sibling `lv`-authored skill, not a patch to an OpenSpec-generated one, so it isn't wiped by `openspec update`/`openspec init --force` the way the `/opsx:propose` patches would be if reapplied by hand instead of via `lv init`.

**Command wiring**: every command in `src/index.ts` is `program.command(...).action(async (...) => { const {runX} = await import('./cli/x.js'); await runX(...).catch(die) })` — a lazy dynamic import per command so CLI startup doesn't eagerly load Mastra/agents. Each `src/cli/x.ts` exports one `runX(...)` doing all the work — no separate controller/service abstraction. Follow this exact shape for new commands.

**Config** (`src/config.ts`): `loadConfig()` walks up from cwd for `.lv.yaml` (repo root marker), merges `.lv.yaml` (committed) + `.lv.local.yaml` (gitignored secrets) + matching uppercased env vars (highest priority), validated by the zod `ConfigSchema` in `src/types.ts`. Every string config value is auto-bridged into `process.env[KEY.toUpperCase()]` so Mastra provider SDKs pick up credentials without extra wiring — this is why `.lv.local.yaml` keys must be named exactly like the env var, lowercased (`openai_api_key` → `OPENAI_API_KEY`).

**Model selection**: models are Mastra `"provider/model"` strings (e.g. `openai/gpt-4o`). `getModelForStep(config, 'bootstrap')` resolves `config.models?.bootstrap ?? config.model` — `bootstrap` is the only remaining per-step override under `.lv.yaml`'s `models:` key. Despite the name, it's no longer read by `lv bootstrap` itself (which makes no LLM call of its own anymore — see "Feature docs pipeline" above); `lv start`'s feature-match/split agents (below) reuse this same `models.bootstrap` config key for their own model selection rather than a step key of their own.

**Agents** — there is no `src/agents/` directory anymore (it held only the bootstrap scan agent, deleted along with `lv bootstrap`'s own LLM calls). The one remaining agent flavor is used by `lv start`, inline in `src/cli/start.ts`:

- **Throwaway single-shot** (`featureMatchAgent`/`featureSplitAgent`, module-level `Agent` instances) — no memory, no tools, used for one-off `generate()` calls where the full context (a ticket's title/description, or a set of candidate existing features) is dumped straight into the prompt, requesting strict JSON back.

`lv bootstrap`'s own docs generation is not an agent at all anymore — it's the `lv-bootstrap` skill/command (see "Feature docs pipeline" above), which runs inside the calling coding agent's own turn instead of a separate Mastra `Agent`/LLM call `lv` would make itself.

There is no persistent, memory-backed agent anymore — that flavor (`analysisAgent`/`designAgent`, LibSQL thread memory for multi-turn `lv answer` iterations) was removed along with the ticket-pipeline commands it served; `getLvDbPath()`'s LibSQL store now only backs `lv start`'s feature-match/split agents.

**Prompts** are centralized in `src/prompts.ts` — not just LLM agent instructions, but any prompt/instructional text constant, period: `buildFeatureMatchPrompt()`/`buildFeatureSplitPrompt()` building `lv start`'s per-call agent messages, `LV_BOOTSTRAP_SKILL_BODY` — the `lv-bootstrap` skill/command's shared instructional body, read by a coding agent, not an LLM `lv` itself calls — plus its per-tool file renderers (`buildLvBootstrapSkillFile()`, `buildLvBootstrapClaudeCommandFile()`, `buildLvBootstrapCursorCommandFile()`), and also `CONTEXT_POINTER`/`CONTEXT_POINTER_LINES` and `ARCHIVE_GUIDANCE` — static text `lv init` writes into `openspec/config.yaml` for a human or OpenSpec's own generated workflows to read, not an LLM call either. `src/cli/init.ts` keeps only the file-IO/orchestration logic (`addContextPointer()`, `addArchiveGuidance()`, `installLvBootstrapSkill()`) that writes them, importing the text itself from `prompts.ts`. Anything asking an LLM to return structured data requests strict JSON with no surrounding text, and is parsed with `extractJson<T>()` (`src/cli/helpers.ts`), which strips a stray ` ```json`/` ```markdown ` fence before `JSON.parse` — models sometimes wrap "no fences" JSON in fences anyway.

**Git integration** (`src/integrations/git/client.ts`) wraps `execa('git', ...)`. `commitAll()` is stage-all (`git add -A`) + conditional commit (no-op if nothing changed) and runs after `lv start` (either entry mode) instead of granular `git add`. **Gotcha**: `git add -A` stages _everything_ dirty in the repo, not just `state.yaml` — running `lv start` while you have unrelated uncommitted source changes sitting in the working tree will sweep those into the change's commit too. Commit or stash unrelated work before exercising it live. `lv start` also pushes (non-fatal — warns and stays local-only if push fails, e.g. no remote/network). `lv bootstrap` deliberately does **not** commit — it prints "review, edit, then commit manually" since generated docs are unverified (headed with an `AUTO_GENERATED_HEADER` comment). `lv init` doesn't commit either — it writes to `openspec/config.yaml` and installs OpenSpec's own files directly, outside `docs/`. `checkoutBranch()` (used by `lv resume <ticket-id>`) tries a plain local `git checkout` first, falling back to fetching and tracking `origin/<branch>` if it doesn't exist locally.

**Lark Base** (`src/tools/lark.ts`) is the only ticket source, used only by ticket-based `lv start`. Auth is app-based, not a static token: `getTenantAccessToken(appId, appSecret)` exchanges `.lv.local.yaml`'s `lark_app_id`/`lark_app_secret` for a `tenant_access_token` per the [internal tenant access token API](https://open.larksuite.com/document/server-docs/getting-started/api-access-token/auth-v3/tenant_access_token_internal), fetched fresh per CLI invocation rather than cached. `lv start` then fetches the ticket record via the Lark Bitable REST API and reads two configurable columns off it — the Feature ID column (`.lv.yaml`'s `lark.feature_id_field`) and the title column (`lark.title_field`, defaults to `"Title"` — the title feeds both `state.yaml`'s `title` field and the branch name's `{summary}`, so it needs to match whatever your Base actually calls that column, e.g. `"Task name"`).

**Self-documentation**: this repo dogfoods its own `docs/features/` convention for its own CLI commands — directories named after the command (`lv-start`, `lv-bootstrap`, `lv-init`, ...), separate from the `Fxxxx`-style IDs `src/engine/feature-id.ts`'s `allocateFeatureIds()` allocates for real product features (those don't match the kebab-case pattern so ID allocation ignores them). Only `lv start`'s inline feature bootstrap calls `allocateFeatureIds()` now — `lv init` no longer allocates feature IDs at all (see "OpenSpec integration" above). `docs/features/INDEX.md` is a hand-maintained markdown table; `updateIndex()` (`src/cli/bootstrap.ts`) appends a fallback bullet line only if no `[<id>]` link already exists anywhere in the file.
