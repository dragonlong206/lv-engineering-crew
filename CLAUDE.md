# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install              # install deps (npm is canonical — package-lock.json is committed; bun.lock is gitignored)
npm run build             # tsup src/index.ts -> dist/ (ESM + .d.ts)
npm run dev -- <args>      # run the CLI from source via tsx, e.g. `npm run dev -- bootstrap F0001`
npm link                  # after building, installs the `lv` binary globally from dist/index.js
npm run mastra             # Mastra dev server at localhost:4111 — inspect agent traces/tool calls
npx tsc --noEmit           # type-check
```

There is no lint script and no automated test suite. Verify changes with `tsc --noEmit`, `npm run build`, and by actually running the relevant `lv <subcommand>` against a scratch repo/doc (see any `src/cli/*.ts` for the command it implements). **Gotcha**: `confirm()`/`promptSelect()` (`src/cli/helpers.ts`, used by `lv resume`) use `readline/promises`. Piped/non-TTY stdin (e.g. `printf "1\nn\n" | npx tsx ...`, used to script these prompts for testing) works fine _across_ separate calls with real async work in between (e.g. a git call, a file read) — but _rapid back-to-back_ `.question()` calls with no intervening await, like `promptSelect()`'s retry-on-invalid-input loop, hang on the second call. This is a Node quirk with piped input specifically; real interactive terminal use is unaffected either way.

## Architecture

`lv` is a spec-driven-development CLI with two independent pipelines that both write into `docs/` of the _target_ repo (this repo dogfoods itself — see below). LV's own job stops at handing context to [OpenSpec](https://github.com/Fission-AI/OpenSpec), which then drives explore → propose → spec → design → tasks → apply through the engineer's coding agent — there is no `lv`-side analysis/design agent or approval gate.

**1. Ticket/change pipeline** — `lv start <ticket-id>` (from a Lark ticket) or `lv start --description "<text>"` (no ticket) creates `docs/changes/<change-id>/state.yaml` (schema: `StateSchema` in `src/types.ts`) — `ticket_id` (optional — absent for description-based changes), `title`, `description`, `feature_ids`, `branch`, `created_at`, `lv_version`. This file is LV's _only_ artifact for a change and the single source of truth for its context — not LibSQL, which only holds Mastra's own thread/memory internals (used solely by `lv bootstrap`'s agents now). `<change-id>` is the ticket ID for ticket-based starts, or `slugify()`d from a short title derived from the description's first line otherwise; it names both `docs/changes/<change-id>/` and, once the engineer runs an OpenSpec workflow, `openspec/changes/<change-id>/` (see "OpenSpec integration" below) — same name, no separate mapping stored. There is no `lv answer`/`lv approve`/`lv design` and no `StateMachine` — once `state.yaml` exists, the engineer drives everything else through OpenSpec directly.

Branch naming is configurable, not hardcoded — `src/engine/branch-naming.ts` renders/parses branch names from `.lv.yaml`'s `branch_types` (a `{ typeName: "prefix/{ticket_id}-{summary}" }` map, e.g. `{ feature: "feature/{ticket_id}-{summary}", hotfix: "hotfix/{ticket_id}-{summary}" }`; defaults to exactly that `{ feature, hotfix }` pair if unset — `DEFAULT_BRANCH_TYPES`) plus `default_branch_type`. `{ticket_id}` and `{summary}` are the only two placeholders; `{summary}` is a `slugify()`d ticket title (or derived short title, for description-based starts), filled in by `lv start` from the fetched Lark record (or the given description). `renderBranchName(config, ticketId, { type?, summary? })` builds a name (used by `lv start`, passing a change-id where a ticket ID would go for description-based starts — the placeholder is generic text substitution, not Lark-specific) — omitting `summary` (as `lv resume`'s no-branch-found fallback does, since it has no ticket title to slugify) drops the placeholder and its preceding separator instead of leaving one dangling. `matchBranch(config, branchName)` tries every configured type's pattern against an arbitrary branch and returns `{type, ticketId}` or `null` (used by every command that re-derives the change ID from the current branch instead of taking it as an argument — `src/cli/resume.ts`, `status.ts`); it captures `{ticket_id}` non-greedily and treats "separator + `{summary}`" as an optional unit, so both a full name and a summary-less fallback name parse back to the same ID — this relies on ticket IDs (Lark Bitable record IDs, plain alphanumeric) and description-derived slugs never containing the literal separator between the two placeholders. `branchGlobs(config)` turns each pattern into a `for-each-ref` glob (both placeholders → `*`) for `listBranchesMatching()` in `src/integrations/git/client.ts`. Adding a new branch-parsing call site means calling `matchBranch()`, never re-deriving a hardcoded prefix.

`lv resume [ticket-id]` (`src/cli/resume.ts`) only resolves and checks out a branch, then prints — it does not dispatch into any further command. Given a ticket ID it searches for branches matching it across _every_ configured type by ticket ID alone via `matchBranch()` (ignoring `{summary}`) — one match checks out directly, multiple prompts via `promptSelect()`, none falls back to `default_branch_type`'s rendered name without a summary (which will only actually exist if the change was never started, so this fallback typically just fails the subsequent checkout); given no ID it uses the current branch if `matchBranch()` recognizes it, otherwise lists all change branches and prompts. Once resolved, it reads `state.yaml` and prints the same summary as `lv status` (shared via `printStateSummary()` in `src/cli/status.ts`), then reminds the engineer to continue via their coding agent's OpenSpec workflow.

**2. Feature docs pipeline** — `lv init [--tool <tool>]` → `lv bootstrap <feature-id>`. `lv bootstrap` populates `docs/features/<feature-id>/{overview.md,design.md,requirements.md}`, independent of any ticket, either from explicit `--paths` (single-shot: dumps matching files into one prompt) or, when `--paths` is omitted, via autonomous codebase exploration — a tool-equipped agent that reads any existing draft and _refines_ it (re-verifying code facts against fresh exploration) rather than overwriting from scratch. `lv start` bootstraps a referenced feature with no `docs/features/<id>/` directory inline (same autonomous-scan mode, seeded with the ticket's title/description) rather than requiring `lv bootstrap` to run first — see `lv-start/inline-feature-bootstrap` under `openspec/specs/`.

`lv init` installs and configures OpenSpec for a chosen coding agent (`src/cli/init.ts`, no Mastra agent involved) and wires OpenSpec's context to LV. It shells out to `openspec init --tools <tool>` via `execa` (same pattern as `src/integrations/git/client.ts`'s git wrapper) — `lv` does not hardcode which coding agents are supported, whatever `openspec init --help` lists is what `--tool` accepts. It then idempotently appends a pointer into `openspec/config.yaml`'s `context:` field naming `docs/features/<feature-id>/{overview.md,design.md}` and `docs/changes/<change-id>/state.yaml`, so every OpenSpec workflow (`/opsx:propose`, `/opsx:apply`, ...) loads LV's context automatically. **Gotcha**: the append is a raw text operation, not a YAML round-trip, specifically to avoid stripping `openspec/config.yaml`'s template comments — it only falls back to parsing+re-dumping via `js-yaml` (losing those comments) when an _active_ (uncommented) `context:` key already exists to merge into.

**OpenSpec integration**: this repo's own `openspec/` directory (schema `spec-driven`, see `openspec/config.yaml`) is both how LV plans its own changes (this file's git history) and the template `lv init` installs into target repos. `openspec/changes/<change-id>/` (proposal.md, `specs/<capability-path>/spec.md` deltas, design.md, tasks.md) is entirely OpenSpec-owned — LV never reads or writes under `openspec/`, except the one-time `context:` pointer write in `lv init`. `.claude/skills/openspec-*`, `.claude/commands/opsx/*`, and `.agents/skills/openspec-*` are what `openspec init --tools <tool>` generates per coding agent; `lv init` never edits these directly (see the `context:`-field decision above, in `design.md` of `openspec/changes/integrate-openspec-workflow/`) since they're regenerated by `openspec update`/`openspec init --force`.

**Command wiring**: every command in `src/index.ts` is `program.command(...).action(async (...) => { const {runX} = await import('./cli/x.js'); await runX(...).catch(die) })` — a lazy dynamic import per command so CLI startup doesn't eagerly load Mastra/agents. Each `src/cli/x.ts` exports one `runX(...)` doing all the work — no separate controller/service abstraction. Follow this exact shape for new commands.

**Config** (`src/config.ts`): `loadConfig()` walks up from cwd for `.lv.yaml` (repo root marker), merges `.lv.yaml` (committed) + `.lv.local.yaml` (gitignored secrets) + matching uppercased env vars (highest priority), validated by the zod `ConfigSchema` in `src/types.ts`. Every string config value is auto-bridged into `process.env[KEY.toUpperCase()]` so Mastra provider SDKs pick up credentials without extra wiring — this is why `.lv.local.yaml` keys must be named exactly like the env var, lowercased (`openai_api_key` → `OPENAI_API_KEY`).

**Model selection**: models are Mastra `"provider/model"` strings (e.g. `openai/gpt-4o`). `getModelForStep(config, 'bootstrap')` resolves `config.models?.bootstrap ?? config.model` — `bootstrap` is the only remaining per-step override under `.lv.yaml`'s `models:` key, since `lv init`/`lv start` no longer run any LLM agent themselves.

**Agents** (`src/agents/`) come in two flavors, both used only by `lv bootstrap`:

- **Throwaway single-shot** (inline `Agent` in `src/cli/bootstrap.ts`) — no memory, no tools, used for one-off `generate()` calls where the full context is dumped straight into the prompt (the `--paths` mode).
- **Stateless but tool-equipped** (`createBootstrapScanAgent()` in `src/agents/bootstrap-agent.ts`) — a factory, not a singleton, because its `listFiles`/`readFile`/`searchCode` tools (`buildCodebaseTools()` in `src/tools/codebase.ts`) close over the target repo's `scan_extensions`/`scan_skip_dirs` (from `.lv.yaml`, defaulting to `DEFAULT_CODE_EXTENSIONS`/`DEFAULT_SKIP_DIRS`), so a fresh agent instance is built per `lv bootstrap`/inline-bootstrap run. No memory, but multi-turn tool-calling to explore the repo. **Gotcha**: Mastra's `Agent.generate()` defaults to `maxSteps: 5` — an exploration agent that needs more turns silently stops with empty `text` and `finishReason: 'tool-calls'` unless you pass a higher `maxSteps` explicitly at the call site.

There is no persistent, memory-backed agent anymore — that flavor (`analysisAgent`/`designAgent`, LibSQL thread memory for multi-turn `lv answer` iterations) was removed along with the ticket-pipeline commands it served; `getLvDbPath()`'s LibSQL store now only backs `lv bootstrap`'s agents.

**Prompts** are centralized in `src/prompts.ts`, not scattered per-agent: `BOOTSTRAP_AGENT_INSTRUCTIONS` (the one remaining `<X>_AGENT_INSTRUCTIONS` constant) plus `buildBootstrap*Prompt(...)` functions building the per-call user message. Anything asking an LLM to return structured data requests strict JSON with no surrounding text, and is parsed with `extractJson<T>()` (`src/cli/helpers.ts`), which strips a stray ` ```json`/` ```markdown ` fence before `JSON.parse` — models sometimes wrap "no fences" JSON in fences anyway.

**Git integration** (`src/integrations/git/client.ts`) wraps `execa('git', ...)`. `commitAll()` is stage-all (`git add -A`) + conditional commit (no-op if nothing changed) and runs after `lv start` (either entry mode) instead of granular `git add`. **Gotcha**: `git add -A` stages _everything_ dirty in the repo, not just `state.yaml` — running `lv start` while you have unrelated uncommitted source changes sitting in the working tree will sweep those into the change's commit too. Commit or stash unrelated work before exercising it live. `lv start` also pushes (non-fatal — warns and stays local-only if push fails, e.g. no remote/network). `lv bootstrap` deliberately does **not** commit — it prints "review, edit, then commit manually" since generated docs are unverified (headed with an `AUTO_GENERATED_HEADER` comment). `lv init` doesn't commit either — it writes to `openspec/config.yaml` and installs OpenSpec's own files directly, outside `docs/`. `checkoutBranch()` (used by `lv resume <ticket-id>`) tries a plain local `git checkout` first, falling back to fetching and tracking `origin/<branch>` if it doesn't exist locally.

**Lark Base** (`src/tools/lark.ts`) is the only ticket source, used only by ticket-based `lv start`. Auth is app-based, not a static token: `getTenantAccessToken(appId, appSecret)` exchanges `.lv.local.yaml`'s `lark_app_id`/`lark_app_secret` for a `tenant_access_token` per the [internal tenant access token API](https://open.larksuite.com/document/server-docs/getting-started/api-access-token/auth-v3/tenant_access_token_internal), fetched fresh per CLI invocation rather than cached. `lv start` then fetches the ticket record via the Lark Bitable REST API and reads two configurable columns off it — the Feature ID column (`.lv.yaml`'s `lark.feature_id_field`) and the title column (`lark.title_field`, defaults to `"Title"` — the title feeds both `state.yaml`'s `title` field and the branch name's `{summary}`, so it needs to match whatever your Base actually calls that column, e.g. `"Task name"`).

**Self-documentation**: this repo dogfoods its own `docs/features/` convention for its own CLI commands — directories named after the command (`lv-start`, `lv-bootstrap`, `lv-init`, ...), separate from the `Fxxxx`-style IDs `src/engine/feature-id.ts`'s `allocateFeatureIds()` allocates for real product features (those don't match the kebab-case pattern so ID allocation ignores them). Only `lv start`'s inline feature bootstrap calls `allocateFeatureIds()` now — `lv init` no longer allocates feature IDs at all (see "OpenSpec integration" above). `docs/features/INDEX.md` is a hand-maintained markdown table; `updateIndex()` (`src/cli/bootstrap.ts`) appends a fallback bullet line only if no `[<id>]` link already exists anywhere in the file.
