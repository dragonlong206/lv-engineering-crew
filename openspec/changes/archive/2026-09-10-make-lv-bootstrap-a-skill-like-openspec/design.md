## Context

See `proposal.md` - Why for the motivation (per-tool-call cost of the current Mastra-agent-driven scan/`--paths` modes). This section covers only the mechanics needed to choose an approach.

Today, `runBootstrap()` (`src/cli/bootstrap.ts`) branches into three modes: `--new-feature` (placeholder, no LLM), `--paths` (an inline Mastra `Agent` makes two parallel `generate()` calls), and the default autonomous-scan mode (`createBootstrapScanAgent()`, `src/agents/bootstrap-agent.ts`, up to 30 tool-calling steps against `buildCodebaseTools()`'s `listFiles`/`readFile`/`searchCode`). Both LLM-driven modes end by writing `docs/features/<feature-id>/{overview.md,design.md}` with `AUTO_GENERATED_HEADER`, then `updateIndex()`, then an optional `syncNewFeatureToLark()`. `lv start`'s inline bootstrap never touches this: it always calls `generateFeatureDocsPlaceholder()` (confirmed in `src/cli/start.ts:377`), so it is unaffected by anything in this change.

`lv init` (`src/cli/init.ts`) installs OpenSpec by shelling out to `openspec init [--tools <tool>]`. `--tool` is optional on `lv init`'s own CLI surface — when omitted, `openspec init` runs its own interactive tool picker, so `lv init` cannot know from `opts.tool` alone which tool(s) were actually selected. The existing patch functions (`addProposeStateAutoload()`, etc.) already solve this by checking for the presence of files OpenSpec is known to generate per tool (`PROPOSE_WORKFLOW_FILES`), not by inspecting `opts.tool`.

Probing `openspec init --tools <tool> --force --no-animation` against scratch directories, across seven of the ~40 tools `openspec init --help` lists (`claude`, `codex`, `cursor`, `cline`, `gemini`, `windsurf`→`devin`, `qwen`), shows a consistent split:
- **The skill file is universal**: every tool gets `<tool-base-dir>/skills/<name>/SKILL.md` with the exact same frontmatter shape (`name`/`description`/`allowed-tools`/`license`/`compatibility`/`metadata`) and byte-for-byte identical body content. Only `<tool-base-dir>` differs (`.claude`, `.cursor`, `.cline`, `.gemini`, `.devin`, or the shared `.agents` for Codex, which also gets a `.agents/skills/.openspec-target` marker recording which tool `.agents` belongs to).
- **The command wrapper is not universal**: Claude nests it (`​.claude/commands/opsx/<name>.md`), Cursor/Qwen flatten it with a dash (`.cursor/commands/opsx-<name>.md`), Cline/Devin put it in a separate `workflows/` directory instead of `commands/` (`.devin/workflows/opsx-<name>.md`), Gemini writes `.toml` instead of Markdown+frontmatter (`.gemini/commands/opsx/<name>.toml`), and Codex has no command file at all — the skill is the only thing invoked ("Commands skipped for: codex (uses skills)").

## Goals / Non-Goals

**Goals:**
- Replace the two LLM-driven bootstrap modes with an `lv-bootstrap` skill (plus a command wrapper where the tool format supports one) that does the exploration and drafting inside the calling agent's own turn.
- Support the skill for every coding agent OpenSpec installs a skill for in the repo — not a fixed, hardcoded list — the same "whatever `openspec init --help` lists" philosophy CLAUDE.md already documents for OpenSpec's own install, extended to `lv`'s own skill.
- Keep `lv` responsible for anything that needs secrets or a stable API contract (Lark sync, `.lv.yaml` reading), so the skill's own instructions stay declarative rather than reimplementing config parsing or Lark's REST protocol in prose.
- Preserve every existing observable behavior that isn't specific to *how* the LLM call happens: auto-generated header, index update, Lark sync, draft-refinement semantics, output-language honoring.

**Non-Goals:**
- Generating a bespoke slash-command file for every tool's own format. Per the Context section, command formats vary too much to generalize safely (nested Markdown, flat Markdown, a separate `workflows/` dir, TOML for Gemini) — `lv` only ships command templates for the shapes it explicitly knows (Claude, Cursor; Decision 4). Every other tool gets the skill only, the same way Codex already works today with OpenSpec's own commands. Adding a new known command shape later is a small, additive follow-up, not something this design blocks.
- Changing `--new-feature` placeholder mode or `lv start`'s inline bootstrap — neither makes an LLM call today, so neither is touched.
- Removing `@mastra/core` as a dependency — `lv start`'s feature-match/split agents still use it.

## Decisions

### 1. Split the CLI into a context step and a finalize step, bracketing the skill's own work
`lv bootstrap <feature-id>` gains two new flags that replace the removed scan/`--paths` LLM modes:
- `--context [--paths <paths>] [--name <name>] [--description <description>]`: no LLM call. Loads `.lv.yaml`, creates the feature directory (`mkdirSync`, so the skill can write into it immediately), reads any existing `overview.md`/`design.md`, and — when `--paths` is given — expands directory paths into a capped file list exactly as `runBootstrapFromPaths()` does today (reusing `listCodeFiles()`). Prints one JSON object: `{ repoRoot, overviewPath, designPath, scanExtensions, scanSkipDirs, outputLanguage, existingOverviewMarkdown?, existingDesignMarkdown?, paths?: string[], name?, description? }`. The skill reads `paths` (or explores freely when absent) using its own `Read`/`Glob`/`Grep` tools — `lv` never reads file *contents* here, only resolves *which* files are in scope, avoiding the double-read (and double token cost) of stuffing file contents into a CLI response that the skill's prompt would just re-paste into its own context.
- `--finalize --title <title>`: no LLM call. Runs `updateIndex()` and `syncNewFeatureToLark()` against the files the skill already wrote. Assumes `overview.md`/`design.md` exist (the skill wrote them); does not touch their content.
- Plain `lv bootstrap <feature-id>` with neither `--new-feature`, `--context`, nor `--finalize` now exits with an error pointing at the `lv-bootstrap` skill/command, instead of silently trying an LLM call that no longer exists.

Rejected alternative: a single `lv bootstrap <feature-id> --paths ...` that also accepts a `--dry-run`-style flag to only print context. Splitting into two explicit flags (`--context`/`--finalize`) reads clearer in the skill's own instructions (two distinct `Bash` invocations, one before exploration and one after) and avoids overloading `--paths`'s existing meaning.

### 2. The skill owns exploration and writing; `lv` owns config, directory creation, and Lark
This mirrors OpenSpec's own division of labor: `openspec instructions <id>` returns template/context/rules and the calling agent writes the file — OpenSpec's CLI never reads or writes artifact *content*. Here, `lv bootstrap --context` is the equivalent of `openspec instructions`, and the skill is the equivalent of the propose/apply workflow that actually writes `proposal.md`/etc.

Rejected alternative: have the skill shell out to `lv` for the actual file write too (e.g., `lv bootstrap --write-overview <file>`). Rejected because Claude Code's own `Write` tool is strictly better for this (the engineer sees a normal diff/review in their existing tool UI) and because piping multi-KB Markdown through a shell argument or stdin adds fragility for no benefit.

### 3. Detect every tool dynamically by globbing for OpenSpec's own skill marker, not a hardcoded tool table
`installLvBootstrapSkill(repoRoot)` runs after the OpenSpec install step and checks for `<dir>/skills/openspec-propose/SKILL.md` under every immediate subdirectory of `repoRoot`. Per the Context section's probe, this exact relative shape (`<tool-base-dir>/skills/openspec-propose/SKILL.md`) is what OpenSpec writes for *every* tool it supports, with no exceptions found across the seven tools probed (including the shared `.agents/` case for Codex-style "generic agent" tools), and OpenSpec always writes a tool's directory directly at the target repo root, never nested. Correction after implementation: a full recursive glob (`**/skills/openspec-propose/SKILL.md`) over the whole tree isn't needed given that — a single-level scan of `repoRoot`'s own subdirectories is enough, is cheaper (no walk of `node_modules`/etc. to exclude), and needs no glob library dependency. For each subdirectory whose marker exists, `lv` writes `<tool-base-dir>/skills/lv-bootstrap/SKILL.md` — with no fixed list of tool names anywhere in this logic, matching how OpenSpec's own installer supports whatever `openspec init --help` lists rather than a set `lv` maintains.

Command-file generation is a separate, smaller step layered on top: a short table of *known command shapes* (currently Claude and Cursor only — see Decision 4) is checked against the same set of matched tool base dirs. A tool whose base dir matches a known shape also gets a command file; every other matched tool (Codex, and any tool `lv` has never special-cased, e.g. Gemini/Cline/Devin/Qwen from the Context probe) gets the skill only. This mirrors Codex's own already-skill-only relationship with OpenSpec's commands, generalized to "whichever tools we haven't written a command template for yet," not "Codex specifically."

Rejected alternative (the previous version of this design): a hardcoded per-tool table mapping tool name -> marker path -> output paths, covering only three tools. Rejected once the Context section's wider probe showed the *skill* path shape is universal across every tool tried (so a hardcoded table would only ever cover a fraction of what OpenSpec supports, requiring manual upkeep every time OpenSpec adds a tool) while the *command* shape genuinely is not generalizable (so a table is still needed there, just scoped to the much smaller "known command shapes" problem instead of "known tools" as a whole).

Rejected alternative: parse `opts.tool`'s comma-separated string directly instead of globbing. Rejected because it's `undefined` on the common "let OpenSpec's own picker decide interactively" path (Context section) — glob-based detection is the one mechanism that covers both the explicit-`--tool`-flag and interactive-picker cases uniformly, and it does so without `lv` needing to know tool names at all.

### 4. Skill and command content, and where it lives
New `src/prompts.ts` constants (replacing `BOOTSTRAP_AGENT_INSTRUCTIONS`, `buildBootstrapScanPrompt`, `buildBootstrapOverviewPrompt`, `buildBootstrapDesignPrompt`):
- `LV_BOOTSTRAP_SKILL_BODY`: one shared Markdown body written into `<tool-base-dir>/skills/lv-bootstrap/SKILL.md` for every tool Decision 3 finds (matching how OpenSpec's own `SKILL.md` body is identical across tools, per the Context section's probe). Content: run `lv bootstrap <feature-id> --context ...` first, explore/read per the `paths` field or freely if absent, apply the same "refine, don't blindly copy" guidance as today's `BOOTSTRAP_AGENT_INSTRUCTIONS`, write `overview.md`/`design.md` with `AUTO_GENERATED_HEADER` prepended (the header text itself moves into the skill body as a literal string, since `lv` no longer prepends it), honor `outputLanguage` from the context JSON, then run `lv bootstrap <feature-id> --finalize --title "<derived-title>"`.
- Skill frontmatter is the same shape for every tool: `name: lv-bootstrap`, `allowed-tools: Bash(lv bootstrap:*)` (scoped to the `bootstrap` subcommand only, not all of `lv`), `metadata.author: lv`.
- Command frontmatter is authored only for the two known shapes today, mirroring what OpenSpec itself generates for each:
  - Claude (`.claude/commands/lv/bootstrap.md`, invoked as `/lv:bootstrap <feature-id>`): `name: "LV: Bootstrap"`, same `allowed-tools` as the skill.
  - Cursor (`.cursor/commands/lv-bootstrap.md`, invoked as `/lv-bootstrap <feature-id>`): `name: "/lv-bootstrap"`, `id: "lv-bootstrap"`, `category: "Workflow"` — no `allowed-tools` field, matching Cursor's own command frontmatter shape.
  - Every other detected tool (Codex, Gemini, Cline, Devin, Qwen, and anything else Decision 3's glob finds): no command file — the skill alone is how the engineer invokes it, same as Codex's existing relationship with OpenSpec's own commands. A future change can add a template for a specific tool's shape (e.g. Gemini's `.toml`) without touching Decision 3's detection logic at all.

### 5. Deletions
Remove `src/agents/bootstrap-agent.ts` entirely. Remove from `src/cli/bootstrap.ts`: the inline `bootstrapAgent`, `runBootstrapFromPaths`, `runBootstrapFromScan`, `generateFeatureDocsFromScan`, `ScanJsonFailureError`. Remove from `src/tools/codebase.ts`: `buildCodebaseTools()` and its Mastra `Tool` wrappers (`listFilesTool`/`readFileTool`/`searchCodeTool`); keep `listCodeFiles()` and the `DEFAULT_CODE_EXTENSIONS`/`DEFAULT_SKIP_DIRS` constants, since `--context`'s path-expansion still needs them. Remove from `src/prompts.ts`: `BOOTSTRAP_AGENT_INSTRUCTIONS`, `BOOTSTRAP_SCAN_JSON_RETRY_NUDGE`, `buildBootstrapScanPrompt`, `buildBootstrapOverviewPrompt`, `buildBootstrapDesignPrompt`. Correction after implementation: `buildOutputLanguageParagraph()` is also removed rather than kept — it existed to build a language-instruction string at prompt-*construction* time from a concrete `outputLanguage` value `lv` already had in hand; the new skill body is a static constant with no such per-call construction step, since the skill itself reads `outputLanguage` from `--context`'s JSON at its own runtime, so the equivalent instruction is written directly into `LV_BOOTSTRAP_SKILL_BODY` as conditional prose instead. `AUTO_GENERATED_HEADER` is kept (still used by placeholder mode, and its literal value is embedded in the new skill body).

### 6. `.lv.yaml`'s `models.bootstrap` stays live — `getModelForStep()` is not deleted
Correction after implementation: `getModelForStep(config, "bootstrap")` (`src/config.ts`) is not dead code to remove. `src/cli/start.ts`'s feature-match and feature-split agents (`featureMatchAgent`/`featureSplitAgent`, out of scope per proposal.md's Impact) also call `getModelForStep(config, "bootstrap")` to pick their own model, reusing the `models.bootstrap` config key rather than a step key of their own. Deleting the function would break `lv start`, which this change must not touch. So: `bootstrap.ts` simply stops importing/calling it (nothing in the new `--context`/`--finalize`/placeholder code paths needs a model), but `getModelForStep()` itself, and `models.bootstrap` in `.lv.yaml`, stay exactly as they are — still load-bearing, just no longer for bootstrap's own generation.

## Risks / Trade-offs

- **[Risk]** An engineer scripting `lv bootstrap <feature-id>` in CI or a non-Claude terminal (relying on the old scan/`--paths` LLM modes) breaks outright. → **Mitigation**: this is the explicit, called-out **BREAKING** change in `proposal.md`; the new no-flag error message names the replacement (`lv-bootstrap` skill/command) so the failure is immediately actionable.
- **[Risk]** `--context`'s JSON contract (field names/shape) becomes an implicit API the skill body depends on; drifting the two independently breaks bootstrap silently (the skill would explore with stale assumptions). → **Mitigation**: both the CLI flag's output shape and the skill body text live in this one change/PR, and `src/prompts.ts` keeps the skill body as a single constant reviewed alongside the CLI change, the same way OpenSpec keeps its own CLI JSON shape and generated skill text in one repo.
- **[Risk]** Glob-based detection (Decision 3) could misfire if an engineer manually deletes a tool's `skills/openspec-propose/SKILL.md` but keeps other files for that tool. → **Mitigation**: low-severity (worst case, the engineer re-runs `lv init` or `openspec update` first); acceptable given it matches the detection style already used for the four existing propose-workflow patches, just generalized from one marker path to a glob pattern.
- **[Risk]** OpenSpec changes the universal `skills/openspec-propose/SKILL.md` shape itself in a future release (unlikely, since it's consistent across every tool probed, but not impossible), silently breaking Decision 3's glob for every tool at once. → **Mitigation**: a mismatch fails safe (no `lv-bootstrap` skill gets installed anywhere, not a crash) and is easy to notice (an engineer running `lv init` sees zero `lv-bootstrap` files appear across every tool, not a subtle per-tool gap); this is a smaller surface than the previous per-tool table version of this risk, since there's now exactly one shape to keep in sync instead of one per tool.
- **[Risk]** The known-command-shapes table (Claude, Cursor) drifts if OpenSpec changes either tool's command frontmatter format in a future release. → **Mitigation**: same class of risk the four existing `PROPOSE_WORKFLOW_FILES`-based patches already accept for Claude; scoped to just two tools rather than growing with every tool OpenSpec adds, since new tools default to skill-only until `lv` explicitly adds their shape.

## Migration Plan

1. Land the skill/command content, the `--context`/`--finalize` flags, and `installLvBootstrapSkill()` together (they're only useful as a set).
2. Delete the Mastra-agent code paths in the same change — no dual-running period, since the ticket's ask is a conversion, not an additive option.
3. Existing repos that already ran `lv init` need to re-run it once to pick up the new skill (and command, for known shapes) for every tool OpenSpec already installed there (`installLvBootstrapSkill()` is idempotent per Decision 3 / the new `lv-init/lv-bootstrap-skill-install` spec).
4. After merging, run the new skill against `docs/features/lv-bootstrap/` and `docs/features/lv-init/` (dogfooding) to refresh their docs, and update CLAUDE.md's "Agents" section to describe the skill-based flow and explain the dynamic detection plus the small known-command-shapes table (Claude, Cursor today), per proposal.md's Impact.
5. Rollback: revert the change; no data migration is involved since `docs/features/**` content format (Markdown + header) is unchanged.
