## Context

See `proposal.md` - Why. This touches the same four layers `lv-start/ui-design-capture` touched — Lark ticket parsing (`src/tools/lark.ts`), config/state schema (`src/types.ts`), `lv start` orchestration (`src/cli/start.ts`), and `lv init`'s propose-specific patch mechanism (`src/prompts.ts` / `src/cli/init.ts`) — plus one addition: unlike a UI design reference, an attachment's content isn't reachable by anything downstream (no `WebFetch`, no browser tool) without the same Lark tenant token `lv start` already holds, so `lv` itself must perform the download, not just capture a pointer.

`fetchTicket()` already normalizes an attachment-shaped field for `ui_design_field` (`normalizeUiDesignRefs()`'s array branch reads `url`/`tmp_url`/`name` off each entry) — but that path only keeps those fields as a reference string, since UI design capture is deliberately reference-only. This capability needs the entry's `file_token` as well (or instead), because Lark's documented way to retrieve an attachment's actual bytes is the Drive media-download endpoint (`GET /open-apis/drive/v1/medias/:file_token/download`, Bearer-authenticated with the same tenant token), not a plain unauthenticated GET on `url`/`tmp_url`.

## Goals / Non-Goals

**Goals:**
- Read one configured Lark attachment column and extract, per file, the metadata needed to download it later (`file_token`, `name`) — a metadata-only read, keeping `fetchTicket()`'s existing "one field in, one first-class value out" shape.
- Actually download each file's bytes during `lv start` (this is the one place this capability differs from `ui-design-capture`) into `docs/changes/<change-id>/attachments/`, using the tenant token `lv start` already has in scope from the ticket fetch.
- Persist the downloaded files' repo-relative paths into `state.yaml`, reusing the same "omit when empty" convention `ui_design` established.
- Make the downloaded files visible specifically to `/opsx:propose` via a dedicated patch into the generated propose workflow file(s), mirroring `PROPOSE_UI_DESIGN_LINE`/`addProposeUiDesignInstruction()`.

**Non-Goals:**
- Content analysis inside `lv` itself (summarizing an image, transcribing a video, etc.) — `lv`'s job stops at getting the bytes onto disk; reading and reflecting on them is the patched `/opsx:propose` workflow's job, same division of labor as `ui-design-capture`.
- Writing back to Lark — this capability is read-only against Lark, like `ui-design-capture`.
- A generic "download any Lark attachment field" abstraction reusable beyond this one ticket-capture field — stays local until a second use case needs it.
- Guaranteeing every attachment downloads successfully — a `tmp_url`/`file_token` can be stale by the time `lv start` runs, or the file can be large enough to time out; those failures are surfaced as warnings, not treated as fatal (see Risks).
- Deduplicating or diffing attachments against a previous `lv start` run on the same change — each run downloads fresh into the same `attachments/` directory, overwriting same-named files. Re-running `lv start` on an already-started change only reaches this code path via the "restart" flow (see `lv-start/resume-or-restart-existing-branch`), which already discards and recreates the branch, so overwriting is consistent with that flow's existing "start clean" semantics.

## Decisions

**Extract metadata in `fetchTicket()`, download in `lv start`.** Splitting these two steps across two functions/layers (rather than downloading inline inside `fetchTicket()`) keeps `fetchTicket()`'s existing contract intact — every other field it reads is a cheap, synchronous-shaped metadata read with no side effect beyond the one ticket GET, and callers other than `lv start` (if any appear later, e.g. a read-only "show ticket" command) shouldn't be forced to pay for file downloads they don't need. `lv start` is the only caller that needs the files on disk, so it calls a separate `downloadTicketAttachments()`-style function after `fetchTicket()` returns, passing the same tenant token. Alternative considered: download inside `fetchTicket()` and return local paths directly — rejected because it conflates "read ticket metadata" with "materialize files on disk," and because `fetchTicket()`'s only other consumer, `larkTicketTool` (the Mastra tool definition in `src/tools/lark.ts`), has no `repoRoot`/change-id in scope to know where to write files.

**Use `file_token` + Drive media-download endpoint, not `url`/`tmp_url`.** Lark's Bitable attachment field read value already carries `url`/`tmp_url` (used today by `normalizeUiDesignRefs()`), but those are browser-facing preview links, not guaranteed stable, authenticated download URLs — the documented way to retrieve a Bitable attachment's actual file content is `GET /open-apis/drive/v1/medias/:file_token/download` with the same `Authorization: Bearer <tenant_access_token>` header every other call in `src/tools/lark.ts` already uses. `file_token` is present on every attachment-field entry Lark returns, so extraction reads `file_token` and `name` (for the output filename) rather than reusing `normalizeUiDesignRefs()`'s shape.

**New field lives on `LarkTicket`, not folded into `rawFields` access at call sites.** Same convention `uiDesignRefs` already follows — `attachments: { fileToken: string; name: string }[]` becomes a first-class field on the ticket returned by `fetchTicket()`.

**Downloaded filenames are sanitized and de-duplicated within one run.** A Lark attachment's `name` comes from whatever the person who uploaded it called the file — it can collide with another attachment on the same ticket, or contain characters unsafe for a filesystem path. The download step sanitizes each name (strip path separators and other unsafe characters) and, on a collision within the same download batch, appends a numeric suffix before the extension (`screenshot.png`, `screenshot-2.png`) rather than silently overwriting one file with another.

**`state.yaml`'s `attachments` is omitted, not `[]`, when there's nothing to record.** Matches `ui_design`'s precedent — keeps `state.yaml` unchanged for the common case (a ticket with no attachment field or an empty one).

**A per-file download failure is caught and reported individually, not batched into one failure.** Mirrors `sync_status`/`sync_feature_id`'s non-fatal posture: one attachment failing to download (stale `file_token`, a transient network error, a file too large) should not cost the engineer every other attachment that did download successfully, nor block `lv start` from creating the branch and persisting state. The download step iterates attachments independently, collects successes into `state.attachments`, and prints one warning per failure.

**Wire the "read the attachment" instruction through a propose-specific file patch, reusing `PROPOSE_UI_DESIGN_LINE`'s anchor and reasoning.** Same decision `ui-design-capture` already made and documented in its own design.md: scope to `/opsx:propose` only (the one workflow that writes `proposal.md`), not the generic `context:` pointer every workflow reads, to avoid token overhead on `/opsx:apply`/`/opsx:sync`/`/opsx:archive` invocations that produce nothing this instruction is about. `addProposeAttachmentInstruction()` reuses the same anchor `addProposeStateAutoload()`/`addProposeUiDesignInstruction()` use (step 1's "ask the user" line) and, like `PROPOSE_UI_DESIGN_LINE`, names the `proposal` artifact explicitly in its own text rather than relying on file position, since step 5 of the generated propose workflow creates every artifact type through one generic per-artifact loop.

**The attachment-reading instruction is simpler than the UI-design one: no fetch, just `Read`.** `PROPOSE_UI_DESIGN_LINE` has to branch on "prefer the Figma MCP server, else `WebFetch`, else cite the raw link" because a UI design reference is a remote URL of unknown shape. An attachment, by the time `/opsx:propose` runs, is already a local file on disk under `docs/changes/<change-id>/attachments/` — the workflow just needs to `Read` it. The new instruction therefore only needs one fallback: when a file's format can't be read directly (a video, or any format the workflow's `Read` tool doesn't support), cite its name/path instead of fabricating a description of content that was never actually viewed.

## Risks / Trade-offs

- **A `file_token` can go stale between the ticket read and the download call** (e.g. the file was deleted in Lark between the two, or Lark's token has a short validity window for some file types) → Mitigation: treat as a per-file failure per the decision above — warn and continue, same posture as every other non-fatal Lark write/read in this codebase.
- **Large attachments (e.g. a video) could make `lv start` noticeably slower or consume meaningful disk space** → Mitigation: acceptable for now — attachments are opt-in via `lark.attachment_field`, and this matches the existing trade-off `lv start` already makes for any other blocking network call in its flow (ticket fetch, feature-table sync). If this proves painful in practice, a size cap or a `--skip-attachments` flag could be added later without changing the spec's core behavior.
- **A misconfigured `attachment_field` name (typo, wrong column) silently produces nothing** rather than erroring → Mitigation: acceptable, matches how an unset/misnamed `ui_design_field`/`project_field` already behaves today (empty result, no error).
- **Downloaded files add to what `git add -A` stages** (per `lv start`'s existing commit-all posture, documented in this repo's CLAUDE.md) → Mitigation: this is consistent with how every other `lv start` output (placeholder feature docs, `state.yaml`) is already committed; an engineer who wants an attachment excluded can remove it from the ticket or `.gitignore` it manually. No new behavior is introduced here beyond what `commitAll()` already does for the rest of `docs/changes/<change-id>/`.
- **A third propose-specific patch function adds more maintenance surface**, same trade-off `ui-design-capture` already accepted for its own third patch → Mitigation: reuses an existing anchor (no new one), and idempotently no-ops the same way the other two do; engineers already know to re-run `lv init` after `openspec update`/`openspec init --force` regenerates these files.

## Migration Plan

No migration needed: `attachment_field` and `attachments` are both optional and additive. Existing `.lv.yaml` files and existing `state.yaml` files remain valid unchanged.
