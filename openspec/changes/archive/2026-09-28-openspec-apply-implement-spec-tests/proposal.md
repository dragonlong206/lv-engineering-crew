## Why

A change's delta specs already spell out its acceptance criteria as `#### Scenario:` WHEN/THEN blocks, but nothing in the OpenSpec workflow `lv init` installs asks the coding agent to turn those scenarios into automated tests. `/opsx:apply` works through `tasks.md` and, unless a task happens to say "write a test", ships the implementation with no test coverage of the very behavior the specs define — so the specs stay prose and regressions go uncaught.

## What Changes

- `lv init` writes an `operations.apply.guidance` entry into the target repo's `openspec/config.yaml`, telling the generated `/opsx:apply` workflow to implement automated tests covering each `#### Scenario:` in the change's delta specs, following the repo's existing test framework, file layout, and naming conventions, and to run them before marking the related tasks complete. This uses the same OpenSpec hook `lv init` already uses for archive guidance: OpenSpec 1.12's `openspec instructions apply --json` returns it as `operationGuidance`, and the generated apply workflow reads it and treats it as advisory.
- The guidance covers a repo with no automated test suite (this repo is one): the agent SHOULD NOT bring in a new test framework on its own initiative, and SHOULD report which spec scenarios still lack automated coverage.
- `lv init` also writes a `rules.tasks` entry into `openspec/config.yaml` so that `tasks.md` generated by `/opsx:propose` (or any tasks-artifact workflow) includes explicit test tasks mapped to the delta spec scenarios. This means apply has concrete, checkable test tasks to work through, not just advisory guidance.
- Both writes are idempotent. Re-running `lv init` leaves exactly one copy of each entry, and each is added independently of the other and of existing archive guidance or custom `apply:`/`rules:` content an engineer has already written.
- This repo's own `openspec/config.yaml` gains both entries when `lv init` is re-run here (dogfooding).

## Capabilities

### New Capabilities
- `lv-init/spec-test-guidance`: `lv init` configures the installed OpenSpec workflow so that task planning includes tests derived from the change's delta spec scenarios, and so that apply implements and runs those tests using the repo's existing test conventions.

## Impact

- `src/prompts.ts`: new `APPLY_TEST_GUIDANCE` and `TASKS_TEST_RULE` text constants.
- `src/cli/init.ts`: new idempotent writers for `operations.apply.guidance` and `rules.tasks`, called from `runInit()`. The write path needs to keep `openspec/config.yaml`'s template comments when neither `operations:` nor `rules:` is active yet, and it must not disturb the existing `addArchiveGuidance()` output.
- `openspec/config.yaml` in target repos (and this repo): new `operations.apply` and `rules.tasks` keys.
- `docs/features/lv-init/{overview.md,design.md}`: gets refreshed at archive time to describe the new guidance.
- No new dependencies. No change to any LV CLI flags or to `state.yaml`.
