## Context

See `proposal.md` - Why. This touches four independent layers — Lark ticket parsing (`src/tools/lark.ts`), config/state schema (`src/types.ts`), the `lv start` orchestration that already threads a "hint" object into inline feature bootstrap (`src/cli/start.ts` → `src/cli/bootstrap.ts` → `src/prompts.ts`), and `lv init`'s existing propose-specific patch mechanism (`PROPOSE_STATE_AUTOLOAD_LINE`/`PROPOSE_LINK_CHANGE_LINE`-style, in `src/prompts.ts` and `src/cli/init.ts`) — so it's cross-cutting enough to warrant recording the approach before implementing.

`fetchTicket()` already has a working pattern for "read one configured column, normalize Lark's read shape, hand back a plain value" — that's exactly what `feature_id_field`/`project_field` do today (see `extractLinkTexts`/`extractLinkRecordIds` and the `isLinkField` detection in `src/tools/lark.ts`). The UI design column doesn't fit that pattern exactly: a Feature ID or Project field is always one Lark field *type* (link or text) per Base, but a UI design field could reasonably be a plain URL/text field (a pasted Figma link) or a Lark attachment field (an uploaded HTML/image/PDF file) — the proposal's Q&A confirmed both must work without the engineer telling `lv` which one it is.

## Goals / Non-Goals

**Goals:**
- Read one configured Lark column and normalize it to `string[]` regardless of whether it's a text/URL field or an attachment field, without a separate `isLinkField`-style metadata lookup (see Decisions).
- Thread that list through `lv start` into `state.yaml` and, for newly-bootstrapped features, into the feature docs — reusing the existing hint-object plumbing rather than adding a parallel path.
- Make the reference visible specifically to `/opsx:propose` — the one workflow that actually writes `proposal.md` — via a dedicated patch into the generated propose workflow file(s), mirroring `PROPOSE_STATE_AUTOLOAD_LINE`/`PROPOSE_LINK_CHANGE_LINE`.
- Have that patch instruct the workflow to actually view/analyze the referenced design content — best-effort, with graceful fallback — specifically when creating the `proposal` artifact, rather than only citing the raw reference string.

**Non-Goals:**
- `lv` itself (the TypeScript ticket-capture code: `fetchTicket()`, `lv start`) fetching, downloading, rendering, or analyzing the referenced asset — that boundary is unchanged (see "Ticket capture stores the reference only" in the spec). Analysis is instructed only inside the patched `/opsx:propose` workflow file(s), never by `lv` itself — see Decisions.
- Writing back to Lark (no ticket update needed here, unlike `sync_feature_id`/`sync_status`) — this capability is read-only against Lark.
- A generic "attachment field" abstraction reusable for other future fields — this stays local to UI design capture until a second use case actually needs it.
- Guaranteeing analysis succeeds for every reference shape — some references (auth-gated Figma pages, expired Lark attachment `tmp_url`s, binary formats the workflow's tools can't render) may not be accessible; the workflow degrades to citing the raw reference rather than failing (see Risks).
- Adding the instruction to the generic `context:` pointer — rejected: that pointer is read by every OpenSpec workflow (`/opsx:apply`, `/opsx:sync`, `/opsx:archive` included), and none of those produces an artifact this instruction is about, so it would be pure token overhead on every invocation of those (see Decisions).

## Decisions

**Normalize by shape-sniffing the value, not by a metadata lookup.** `feature_id_field` needs `isLinkField()` (a field-metadata API call) because an empty Link field and an empty text field read back identically — the code can't tell "no value" from "wrong field type" without asking Lark what the field *is*. UI design capture doesn't have that ambiguity: a text/URL field's read value is a string (or a `{text, link}` object for a URL-type field); an attachment field's read value is always an array of file objects with `url`/`tmp_url`/`name`. Because "capture reference only" means we never need to distinguish "empty link field" from "empty text field" (both just produce zero references), a single shape-sniffing normalizer avoids the extra Lark API round-trip `isLinkField()` requires. Alternative considered: mirror `isLinkField()` for symmetry with `feature_id_field` — rejected as unnecessary API cost for no behavioral gain here.

**New field lives on `LarkTicket`, not folded into `rawFields` access at call sites.** `fetchTicket()` already extracts `featureIds`/`title`/`description`/`projectRecordIds` as first-class fields rather than making callers dig through `rawFields`; `uiDesignRefs: string[]` follows that same convention for consistency.

**`state.yaml`'s `ui_design` is omitted, not `[]`, when there's nothing to record.** Matches `openspec_changes`'s pattern of only appearing when meaningful, and keeps `state.yaml` unchanged for every ticket that has no design reference — which is the common case today, before this capability exists anywhere in history.

**Feature docs get the reference via the existing `BootstrapScanHint`, as a new optional field, not a new parameter.** `src/cli/start.ts` already builds a hint object (`{ name, description }`) for inline bootstrap; adding `uiDesignRefs?: string[]` to `BootstrapScanHint` and threading it into `buildBootstrapScanPrompt()` reuses the exact call path `lv start` already exercises, rather than adding a second argument that every intermediate function has to forward.

**Wire the analysis instruction through a propose-specific file patch, not the generic `context:` pointer.** `lv init` has two mechanisms for getting instructions into OpenSpec's workflows: (1) `CONTEXT_POINTER_LINES`, appended into `openspec/config.yaml`'s `context:` field by `addContextPointer()`, read generically by *every* workflow (explore/propose/apply/sync/archive) each time it loads `openspec instructions`; and (2) propose-specific patches like `PROPOSE_STATE_AUTOLOAD_LINE`/`PROPOSE_LINK_CHANGE_LINE`, inserted directly into the generated `.claude/commands/opsx/propose.md` (and paired skill files) by dedicated `addProposeXxx()` functions in `src/cli/init.ts`. An earlier version of this design used the generic `context:` pointer, reasoning that no *timing* constraint forced a file-specific patch (unlike the other two, which must run before `openspec instructions` is ever read). That reasoning was correct but beside the point: timing isn't the only reason to scope a patch to one workflow file — relevance is. Only `/opsx:propose` writes `proposal.md`, the one artifact this instruction is about; `/opsx:apply` implements already-decided work, and `/opsx:sync`/`/opsx:archive` touch neither proposal content nor anything design-relevant. Putting the instruction in `context:` means every single invocation of those other three workflows carries ~80-100 tokens of Figma-MCP/`WebFetch`/`Read` instructions it will never act on, and risks a workflow (e.g. `/opsx:apply`) literally trying to re-fetch/re-analyze the design on its own initiative instead of trusting what `/opsx:propose` already captured in `proposal.md`/`design.md` — duplicated work and a second, possibly divergent read of the same asset. So this instead adds a third propose-specific patch: `PROPOSE_UI_DESIGN_LINE` (`src/prompts.ts`) and `addProposeUiDesignInstruction()` (`src/cli/init.ts`), reusing the same anchor as `addProposeStateAutoload()` (step 1's "ask the user" line) since it's the natural place to mention the same matched `state.yaml`. Because step 5 of the generated propose workflow creates every artifact type (proposal/specs/design/tasks) through one generic per-artifact loop with no artifact-specific anchor to patch into, the instruction text itself names the `proposal` artifact explicitly ("specifically when you create the `proposal` artifact... not the other artifact types") rather than relying on file position to scope it — the whole workflow file is loaded into the agent's context at once regardless of which step it's textually near.

**Analysis lives in the OpenSpec workflow's own execution, not in new `lv` code.** `lv` is a plain Node CLI — its ticket-capture path has no wiring to fetch an arbitrary URL and interpret what's on it (no LLM call happens between `fetchTicket()` and writing `state.yaml`, and there's no vision-capable model call in that path at all). Whichever OpenSpec workflow the engineer runs, by contrast, already executes as a tool-equipped Claude agent with `WebFetch` (for URLs) and `Read` (for local files, including images and PDFs) available. So "view the design and let it inform the proposal" is added as an instruction patched into the `/opsx:propose` workflow file(s), not as a new capability in `lv`'s codebase — this keeps the "ticket capture stores the reference only" boundary intact while adding real analysis at the layer that already has an LLM and tools in the loop. Alternative considered: give `lv` its own fetch-and-summarize step (e.g. another Mastra agent call) before persisting to `state.yaml` — rejected because it would duplicate tool capability OpenSpec workflows already have, force `lv start` to make a blocking network/LLM call during ticket ingestion, and couple ticket capture to Lark-specific asset availability at the wrong layer.

**For a Figma reference, prefer Figma's own Dev Mode MCP Server over a plain `WebFetch`, when one is configured.** Figma ships an official MCP server (local, via the Figma desktop app's Dev Mode, at `http://127.0.0.1:3845/mcp`; or remote, at `https://mcp.figma.com/mcp`, OAuth-gated) exposing tools like `get_code`, `get_screenshot`, `get_variable_defs`, and `get_metadata` against a specific Figma URL (one that includes a `node-id`). This is materially better than `WebFetch` for a Figma link: Figma pages are a JS canvas app, not server-rendered HTML, so a plain HTTP fetch typically returns little to nothing usable, and the file is often behind a login `WebFetch` can't pass. The propose-specific instruction therefore tells the workflow to check whether a Figma MCP server is configured in the engineer's own environment (an `lv`/`lv init`-independent fact — the engineer sets this up themselves, e.g. via `claude mcp add`) and prefer its tools for Figma URLs specifically, falling back to `WebFetch` (and then to citing the raw link) when no such server is available. `lv` does not install, configure, or depend on the Figma MCP server itself — this is purely an instruction for the workflow to use it *if already present*, consistent with "capture reference only" on `lv`'s side.

## Risks / Trade-offs

- **Attachment file objects vary by Lark API version** (some return `tmp_url` only, valid for a limited time, rather than a stable `url`) → Mitigation: prefer `url` when present, fall back to `tmp_url`, then `name` alone as a last resort — never throw on an unrecognized shape, just drop that entry (matches the existing `extractLinkRecordIds`/`extractLinkTexts` posture of returning `[]` rather than throwing on unexpected input).
- **A misconfigured `ui_design_field` name (typo, wrong column) silently produces no references** rather than erroring → Mitigation: acceptable, matches how an unset/misnamed `project_field` already behaves today (empty result, no error) — consistent with treating Lark field misconfiguration as non-fatal throughout this codebase.
- **A workflow's available tools may not support every reference format** — `WebFetch` fetches and interprets a URL's content but may not render a Figma prototype meaningfully via plain HTTP (mitigated for Figma specifically by preferring the Figma MCP server, see Decisions) and doesn't download binary files for direct viewing; `Read` supports local image/PDF files but not remote URLs directly → Mitigation: instruct the workflow to make a best-effort attempt with whatever tools are available and gracefully fall back to citing the raw reference text when it can't meaningfully access the content — never block artifact creation on failed analysis (same non-fatal posture as the rest of this capability).
- **The Figma MCP server may not be configured in every engineer's environment** — it's an opt-in setup the engineer does themselves (local Figma desktop app in Dev Mode, or a remote OAuth connection), not something `lv` installs or can detect at `lv init` time → Mitigation: the propose-specific instruction only says to *prefer* the MCP server *when configured*; a workflow with no such server simply falls through to `WebFetch`, so nothing breaks for engineers who haven't set it up.
- **Scoping the instruction to `/opsx:propose` only means `/opsx:apply`/`/opsx:sync` never independently look at the design** — they rely entirely on what `/opsx:propose` already captured in `proposal.md`/`design.md` text. If that capture turns out to be insufficient for implementation (e.g. a detail only visible in the Figma file, never written down), apply has no fallback to go re-check the source → Mitigation: acceptable for now — apply's job is implementing an already-decided design, not re-deriving it from raw asset content; if this proves insufficient in practice, a similar propose-specific-style patch could later be added to the apply workflow specifically, rather than reopening the generic `context:` pointer.
- **A third propose-specific patch function adds more maintenance surface** — a third regex anchor (reused from `addProposeStateAutoload()`, so no *new* anchor) and a third idempotency check across three generated files → Mitigation: reuses an existing anchor rather than introducing a new one, and each patch function already independently no-ops via `openspec update`/`openspec init --force` regenerating these files — engineers already know to re-run `lv init` after either, per the existing `PROPOSE_STATE_AUTOLOAD_LINE`/`PROPOSE_LINK_CHANGE_LINE` precedent (same pre-existing risk, not a new one this change introduces).

## Migration Plan

No migration needed: `ui_design_field` and `ui_design` are both optional and additive. Existing `.lv.yaml` files and existing `state.yaml` files remain valid unchanged.
