## Context

See `proposal.md` - Why for the motivation. Relevant current state:

- `src/cli/init.ts` runs a throwaway single-shot agent over raw requirement docs, allocates `Fxxxx` IDs via `allocateFeatureIds()`, and writes `docs/features/<id>/overview.md`.
- `src/cli/start.ts` fetches a Lark ticket, allocates/bootstraps feature IDs inline (`lv-start/inline-feature-bootstrap`), creates a branch, then calls the memory-backed `analysisAgent` (`src/agents/analysis-agent.ts`) to write `docs/changes/<ticket-id>/1.proposal.md`, and records progress in `state.yaml` via `StateSchema` (`src/types.ts`) — `current_step: "analysis"`, `steps.analysis.status: "in_progress"`.
- `src/cli/answer.ts`, `approve.ts`, `design.ts` drive the rest of the pipeline (multi-turn Q&A, approval, then the `designAgent` writing `3.design.md`/`5.tasks.md`/`2.specs/*.md`), gated by `StateMachine.canRun()` (`src/engine/state-machine.ts`).
- `src/cli/resume.ts` dispatches based on `state.steps[current_step].status`, and `src/cli/status.ts` prints per-step iteration/token/duration stats — both read fields this change removes.
- OpenSpec is already vendored into this repo (`openspec/`, `.claude/skills/openspec-*`, `.claude/commands/opsx/*`, `.agents/skills/*`), installed via the OpenSpec CLI (`openspec init --tools <tool>`), and already supports a project-wide `context:`/`rules:` block in `openspec/config.yaml` that gets threaded into every artifact's `openspec instructions <id> --json` output.

## Goals / Non-Goals

**Goals:**
- Make `lv init`'s job "get OpenSpec installed and pointed at LV's context sources," not "generate documentation content."
- Make `lv start`'s job "materialize `docs/changes/<change-id>/state.yaml` as context," not "run an agent that writes a document."
- Keep `docs/features/` and `lv bootstrap` exactly as they are — this change only touches the ticket pipeline (`init`, `start`, `answer`, `approve`, `design`, `resume`, `status`) and `state.yaml`'s shape.

**Non-Goals:**
- Building custom per-agent skill/command templates beyond what the OpenSpec CLI already generates and this change augments.
- Any GitLab/CI integration, or resurrecting `lv archive-change-docs` — untouched, still future work.
- Migrating or converting any change already mid-pipeline under the old `1.proposal.md`/`3.design.md` scheme (see Migration Plan).

## Decisions

### 1. Context injection point: `openspec/config.yaml`'s `context:` field, generated per-change, not hand-edited skill files
`openspec instructions <artifact> --change <name> --json` already returns a `context` field sourced from `openspec/config.yaml`'s top-level `context:` key (confirmed via the scaffolded `openspec/config.yaml` in this repo, which documents exactly that field). Rather than `lv init` rewriting the *installed* skill/command markdown files under `.claude/skills/openspec-*` or `.claude/commands/opsx/*` — which are OpenSpec's own generated artifacts, liable to be overwritten by a future `openspec update` — `lv init` and `lv start` instead:
- `lv init` writes a static pointer into `openspec/config.yaml`'s `context:` (e.g. "Feature docs live in `docs/features/<id>/`; the active change's ticket/description context lives in `docs/changes/<current-branch's-change-id>/state.yaml` — read it before proposing.") once, at install time.
- `lv start` does not need to touch `openspec/config.yaml` per-change: the pointer above is generic enough (branch name resolves the change id) that no per-change rewrite is needed. `state.yaml`'s location is deterministic from the change id.

This keeps LV's edits confined to one file it fully owns the relevant key of (`context:`), instead of parsing and patching OpenSpec-owned generated files whose format isn't a contract LV controls.

**Alternatives considered:** editing the generated `.claude/commands/opsx/propose.md` etc. directly — rejected because those files are regenerated by `openspec update`/`openspec init --force` and are per-coding-agent (Claude Code, Codex, Cursor, ...), multiplying the surface LV has to keep in sync for no benefit over the one config field OpenSpec already exposes for exactly this purpose.

### 2. `lv init` delegates entirely to the OpenSpec CLI for agent support
`lv init [--tool <tool>]` shells out to `openspec init --tools <tool>` (via `execa`, matching the existing pattern in `src/integrations/git/client.ts`) instead of LV maintaining its own list of supported coding agents. If `--tool` is omitted, it invokes `openspec init` with no `--tools` flag so OpenSpec's own interactive prompt runs. This is what "supports whatever set of agents the installed OpenSpec CLI supports" (per proposal) means concretely: LV has zero agent-specific code.

**Alternatives considered:** hardcoding `claude | codex | cursor` in a `lv init` enum — rejected per the user's explicit answer ("all coding agents that OpenSpec supports"), and because OpenSpec's own `--tools` list already changes over time (currently 30+ values per `openspec init --help`); hardcoding would drift immediately.

### 3. `lv init` drops raw-document splitting outright; no flag-gated legacy path
Per the proposal's scope decision, `runInit()`'s existing body (single-shot agent over `docPaths`, `allocateFeatureIds()`, `writeFile(overview.md)`, `updateIndex()`) is deleted, not kept behind a flag. `src/prompts.ts`'s `buildInitPrompt`/`AUTO_GENERATED_HEADER` (the latter still used by `bootstrap.ts`, so only the `init`-specific prompt builder goes) and the `initAgent` definition go with it. The `<docs...>` positional argument and `--id-prefix`/`--id-digits` options move off `lv init` in `src/index.ts`; `--id-prefix`/`--id-digits` had no other caller so they're removed, not relocated.

### 4. `state.yaml` shape shrinks to what a context-only file needs
`StateSchema` (`src/types.ts`) drops `current_step`, `steps.{analysis,design}` (`StepRecordSchema`, `StepStatusSchema`), and `STEPS`/`Step` — nothing in the new pipeline tracks step status, iterations, tokens, or duration, because there's no LV-run agent step left to instrument. The new shape:

```yaml
ticket_id: PROJ-1234       # present only for ticket-based starts
description: <free text>    # present only for description-based starts; ticket's description when ticket-based
title: <string>              # ticket title, or a short title derived from the description
feature_ids: [F0007]
branch: lv/PROJ-1234
created_at: 2026-08-26T09:02:00+07:00
lv_version: 0.1.0
```
Exactly one of `ticket_id` or a standalone `description`-only mode is set; when starting from a ticket, `description` is also populated from the ticket's description field so the shape is uniform for the OpenSpec context pointer to read regardless of entry mode. `change_id` is not a separate field — it's the ticket id, or a slugified id derived from the description/title, and it names the `docs/changes/<change_id>/` directory itself (consistent with the "same name" answer on how this links to the OpenSpec change).

**Alternatives considered:** keeping `current_step`/`steps` for potential future re-use by a re-introduced LV-run step — rejected as speculative; `StateSchema` can grow again if a future phase needs it, per the project's stated preference against designing for hypothetical requirements.

**Implementation note:** the description-mode change-id must not contain the branch pattern's separator character (`-` by default) — `matchBranch()`'s non-greedy `{ticket_id}` capture (`src/engine/branch-naming.ts`) assumes the id itself is hyphen-free, same as a real Lark ticket ID. `slugify()` produces hyphens, so the change-id uses an underscore-substituted variant of it instead of reusing `slugify()` directly, and the branch is rendered with no separate `{summary}` (the change-id already reads as the summary) to avoid duplicating it.

### 5. `lv answer` / `lv approve` / `lv design` / `StateMachine` are deleted, not deprecated
Per the proposal (**BREAKING**) and the explicit scope decision to remove entirely: `src/cli/answer.ts`, `approve.ts`, `design.ts`, `src/engine/state-machine.ts`, `src/agents/analysis-agent.ts`, `src/agents/design-agent.ts`, and their `src/prompts.ts` entries (`ANALYSIS_AGENT_INSTRUCTIONS`, `buildAnalysisPrompt`, `DESIGN_AGENT_INSTRUCTIONS`, `buildDesignPrompt`, and any `extractJson`-based structured-output helpers used only by them) are deleted outright. Their `program.command(...)` registrations in `src/index.ts` are removed.

### 6. `lv resume` keeps branch resolution, drops step dispatch
`resume.ts`'s two responsibilities split cleanly: resolving which branch/change to check out (by ticket ID across configured branch types, or from the current branch, or via `promptSelect()` over all ticket branches) has nothing to do with the removed step machinery and is kept as-is. The back half — reading `state.steps[current_step]`, prompting to approve, calling `runApprove()`/`runDesign()` — is deleted along with those commands. After checkout, `lv resume` prints the resolved change's `state.yaml` summary (ticket/description, feature IDs, branch) and tells the engineer to continue with their coding agent's OpenSpec workflow, mirroring what `lv status` now shows.

### 7. `lv status` reports change context, not step progress
`status.ts` drops `printStep()` and the `current_step`/`steps` fields it reads, printing instead: ticket id or description, title, feature ids, branch, created_at — i.e., a dump of the new `state.yaml` shape. No new information is invented; it stops reporting fields that no longer exist.

## Risks / Trade-offs

- **[Risk]** `openspec update`/`openspec init --force` could someday change how `context:` is structured or move it elsewhere in `openspec/config.yaml`, silently breaking LV's pointer. → **Mitigation**: `lv init` writes the pointer idempotently (check-then-append, not blind overwrite) and `lv doctor`-equivalent output (or just `lv init` re-run) can detect and re-apply it; this is a one-paragraph text block, cheap to regenerate.
- **[Risk]** Deleting `StepRecordSchema`/`current_step` is a breaking schema change — any `state.yaml` written by the old pipeline (on a ticket branch already mid-flight when this change lands) will fail to parse under the new `StateSchema`. → **Mitigation**: see Migration Plan; this is an accepted one-time breakage given the project has no production tickets yet (pilot phase).
- **[Trade-off]** Moving context-loading into `openspec/config.yaml`'s single global `context:` field means it applies uniformly to every change, not per-change-customizable the way editing per-change skill instructions might allow. Accepted: the pointer text itself is generic ("read the current change's `state.yaml`"), so no per-change customization is actually needed.

## Migration Plan

- This repo has no in-flight tickets under the old `docs/changes/<ticket-id>/1.proposal.md` scheme at the time of writing (`docs/changes/` does not exist yet in this repo — confirmed via `ls docs/`). No data migration script is needed; the schema change ships as a breaking change with no compatibility shim.
- Rollout is a single change: land the new `lv init`/`lv start`/`StateSchema`, delete the old commands/agents, update `README.md`/`CLAUDE.md`.
- No rollback plan beyond `git revert` — there's no external state (no DB rows, no deployed service) to unwind.

## Open Questions

- Exact wording/format of the `context:` pointer `lv init` writes into `openspec/config.yaml` — left to implementation; it must name the feature-docs path and the state.yaml path but doesn't affect this change's specs or task breakdown.
- Whether `lv init` should also pass through OpenSpec's other install flags (`--language`, `--profile`) — not required by the proposal; can be added later without a spec change since it's purely additive CLI surface.
